# Техническое задание на разработку UptimeMonitor

**Продукт:** сервис мониторинга доступности сайтов с продажей подписки  
**Версия документа:** 3.0  
**Дата:** 1 октября 2026 года  
**Целевой релиз:** коммерческая версия 1.0 для запуска в России  
**Исполнитель:** разработчик проекта  
**Статус:** спецификация коммерческого запуска

Документ определяет требования к работающему коммерческому сервису: реальные платежи в рублях, мониторинг адресов, предварительно одобренных владельцем сервиса, и Telegram-уведомления о сбоях и восстановлении. Версия 3.0 заменяет демонстрационные ограничения редакции 2.0. Тестовые окружения используются для разработки и не заменяют приёмку реальной оплаты и production-эксплуатации.

## 1 Назначение продукта

Разработать и разместить в интернете сервис, в котором пользователь регистрируется, подаёт адрес своего сайта на одобрение, подключает мониторинг, привязывает Telegram и покупает платный доступ с реальным списанием средств.

Сервис выполняет HTTP-проверки по расписанию, сохраняет историю, показывает статистику и сообщает о подтверждённых сбоях и восстановлении. Проверки продолжаются независимо от открытого браузера пользователя.

Результат используется как действующий небольшой SaaS-бизнес, проект для портфолио и учебный проект с воспроизводимой сборкой, тестами и CI/CD. Первая покупка независимым клиентом является бизнес-целью; собственная контрольная оплата подтверждает интеграцию, но не считается такой продажей. Выручка и прибыль учитываются отдельно.

HTTP 200 главной страницы не подтверждает работоспособность всех функций сайта. Сервис измеряет ответы из одной точки размещения, а не доступность из всех регионов и не полную загрузку страницы браузером.

## 2 Границы коммерческого релиза

### 2.1 Обязательный состав

- Публичные страницы услуги, тарифов, контактов и условий обслуживания.
- Регистрация, подтверждение email, восстановление доступа, сессии и изоляция пользователей.
- Бесплатный тариф и реальная покупка Pro на 30 суток через ЮKassa.
- Заявки на адреса и обязательное предварительное одобрение каждого URL владельцем сервиса.
- Управление мониторами, постоянные HTTP-проверки, история и статистика.
- Подключение личного Telegram-чата, инциденты, уведомления о сбое и восстановлении.
- Устойчивая очередь уведомлений в PostgreSQL, повторы и журнал доставки.
- Реальная обработка подтверждений платежей, периодическая сверка и учёт возвратов.
- PostgreSQL, SQL-исследование, Redis-кеш, React-кабинет и техническое SEO.
- Docker Compose, Nginx, HTTPS, GitHub Actions CI/CD, резервные копии и восстановление.
- Контроль работы самого сервиса, регламенты поддержки и коммерческая приёмка.

### 2.2 Принятые решения

**A-01. Платежи.** Россия, валюта RUB. Базовый провайдер — ЮKassa, оплата на размещённой у провайдера странице. Применяется одностадийная оплата с capture=true. Пользователь покупает доступ на 30 суток и продлевает его вручную; автоматических списаний нет. Смену провайдера оформляют отдельным изменением адаптера и требований приёмки.

**A-02. Адреса.** Каждый точный нормализованный URL одобряется владельцем сервиса для конкретного пользователя. Одобрение одного домена, пути или чужого пользователя не разрешает остальные адреса. Платная подписка не обходит модерацию. Автоматическое разрешение произвольных сайтов не входит в релиз.

**A-03. Пользователи.** Один аккаунт управляет только своими адресами, мониторами, платежами и личным Telegram-чатом. Команды, корпоративные аккаунты и групповые Telegram-чаты не поддерживаются.

**A-04. Инфраструктура.** Один VPS с Linux и одна PostgreSQL. API, один worker проверок и один dispatcher фоновых доставок/сверки работают отдельными процессами из общего backend-образа. Dispatcher не выполняет HTTP-проверки сайтов. Redis — необязательный кеш, а не хранилище оплаты или очереди.

**A-05. Интерфейс.** Публичные страницы формируются FastAPI в HTML; React/Vite используется в кабинете. SSR/SSG публичной части допускается отдельным решением при сохранении требований SEO.

**A-06. Управление.** Одобрение/отзыв URL, тарифы и операторские действия выполняются защищёнными CLI-командами на сервере с журналированием. Пользовательский API не содержит маршрутов выдачи себе роли или одобрения URL.

### 2.3 За пределами версии 1.0

Автосписания, хранение банковских карт, промокоды, несколько валют, команды пользователей, веб-панель администратора, социальный вход, уведомления о сбоях по email, публичные status pages, несколько регионов проверок, Celery, Kafka, Kubernetes и WebSocket. Транзакционные письма для подтверждения email и восстановления пароля входят в релиз.

Возвраты выполняются оператором через кабинет/ API провайдера и учитываются приложением; самостоятельная форма возврата пользователем не обязательна. Перед коммерческим включением должны быть завершены условия запуска из раздела 15.4.

## 3 Роли и основные сценарии

| Роль | Возможности |
|---|---|
| Посетитель | Чтение услуги, тарифов, правил разрешённых URL и условий; регистрация |
| Пользователь | Заявки на URL, собственные мониторы/история, Telegram, реальные покупки и восстановление аккаунта |
| Владелец сервиса | Модерация URL, тарифы, поддержка, возвраты, блокировка злоупотреблений, эксплуатация и аудит |

Основной сценарий:

1. Пользователь регистрируется, подтверждает email и получает Free.
2. Подаёт точный URL и пояснение о праве мониторить сайт.
3. Владелец проверяет заявку и одобряет либо отклоняет её с причиной.
4. Для одобренного адреса пользователь создаёт монитор в пределах тарифа.
5. Привязывает личный Telegram-чат и подтверждает привязку в кабинете.
6. Worker сохраняет проверки; при подтверждённом сбое создаётся инцидент и уведомление.
7. После подтверждённого восстановления приходит отдельное сообщение с временем события.
8. При необходимости пользователь оплачивает Pro на странице ЮKassa; backend проверяет платёж и расширяет лимит до пяти мониторов.
9. После окончания оплаченного периода применяется Free без удаления истории; продление выполняется новой покупкой.

Модерация и возможность подключить Telegram доступны до оплаты. Кабинет заранее объясняет, что покупка Pro расширяет квоту, но не гарантирует одобрение любого URL. Управление доступом и правами выполняет backend.

## 4 Тарифы и подписка

| Параметр | Free | Pro |
|---|---|---|
| Цена | 0 | 499 RUB за 30 суток |
| Срок | Без ограничения | 30 × 24 часа |
| Одновременно проверяемые мониторы | 1 | 5 |
| Интервал цикла проверок | 60 секунд | 60 секунд |
| Telegram о сбое и восстановлении | Да | Да |
| Хранение подробной истории | 31 сутки | 31 сутки |
| Предварительное одобрение URL | Обязательно | Обязательно |

499 RUB — начальная реальная цена, изменяемая владельцем в данных тарифа. Сумма хранится целым числом в копейках; стоимость, валюта и оплачиваемый период фиксируются backend в покупке. Изменение цены не меняет уже созданную покупку.

**SUB-01. Действие.** Pro действует, пока now < paid_until. При now >= paid_until действует Free. Используется время backend в UTC.

**SUB-02. Продление.** Подтверждённая покупка добавляет 30 суток к max(now, paid_until). Одно успешное списание применяется ровно один раз. Две разные одновременно оплаченные покупки добавляют оба периода.

**SUB-03. Хранение.** До 20 мониторов на аккаунт, включая выключенные; до 20 заявок на URL, из них не более 5 в состоянии pending. Превышение возвращает 409. Это ограничения продукта, показанные в кабинете.

**SUB-04. Включение.** Создание включённого монитора и включение существующего выполняются атомарно с проверкой квоты и одобрения адреса. Два параллельных запроса не обходят лимит. Выключение разрешено и при временном превышении квоты после окончания Pro.

**SUB-05. Окончание.** История и мониторы сохраняются. Из включённых мониторов с действующим разрешением проверяются первые N по created_at ASC, id ASC, где N — лимит текущего тарифа. Остальные имеют paused_by_plan. Отозванные/небезопасные адреса не занимают место среди эффективных мониторов.

**SUB-06. Возобновление.** После продления ранее включённые мониторы возобновляются в пределах пяти при действующем разрешении URL. После повторного одобрения адреса действует то же правило. Поведение явно объясняется в кабинете.

**SUB-07. Актуальность.** API и worker вычисляют тариф по текущему времени; отдельная задача истечения не является условием применения Free. Уже начатая проверка может завершиться, новые сверх лимита не начинаются.

**SUB-08. Учёт доступа.** Для каждой покупки хранится отдельное начисление оплаченного времени; paid_until является итогом начислений и подтверждённых корректировок. Возврат учитывается по разделу 9.4 и не отменяет время, приобретённое другими платежами. Операторские изменения требуют причины и записи аудита.

## 5 Учётные записи и сессии

**AUTH-01. Регистрация.** Email, пароль и подтверждение пароля. Email нормализуется strip + lower и уникален в БД. Пароль от 12 до 128 символов, пробелы допустимы и не обрезаются. Повторный email — 409. Перед регистрацией отображаются условия обслуживания и обработки данных, сохраняется принятая версия документа и время.

**AUTH-02. Хранение.** Пароли хешируются Argon2id. Исходные пароли, токены, cookie и секреты не записываются в логи.

**AUTH-03. Вход.** Неверные email/пароль дают одинаковый ответ 401. До 10 попыток с IP за минуту; превышение — 429. IP извлекается только из доверенных proxy-заголовков. Повторные неуспешные входы в один аккаунт также ограничиваются.

**AUTH-04. Сессия.** Непрозрачный токен с энтропией не менее 256 бит; в БД — его хеш. Сессия действует 12 часов без скользящего продления. Production-cookie: HttpOnly, Secure, SameSite=Lax. Выход отзывает текущую сессию; смена/сброс пароля — все сессии.

**AUTH-05. CSRF.** Изменяющие запросы с cookie требуют связанный с сессией CSRF-токен и допустимый Origin. Для register/login действует отдельная проверка Origin; существующая сессия для регистрации не требуется. Webhook ЮKassa и Telegram используют свои правила проверки. CORS не разрешает произвольные источники с credentials.

**AUTH-06. Владение.** Мониторы, URL-заявки, проверки, инциденты, Telegram и платежи доступны только владельцу. Чужой идентификатор — 404, недействительная сессия — 401. Правило действует до чтения защищённого кеша.

**AUTH-07. Подтверждение email.** До подтверждения доступны вход и повторная отправка письма; покупка и создание заявок/мониторов запрещены с email_not_verified. Одноразовый токен хранится хешем, действует 24 часа. Новый токен отзывает предыдущий. Повторная отправка — не чаще раза в минуту и не более пяти раз в час на аккаунт.

**AUTH-08. Восстановление.** Запрос сброса пароля всегда даёт одинаковый 202 независимо от наличия email. Токен с энтропией 256 бит действует 30 минут, используется один раз и хранится хешем. После смены пароля старые сессии и остальные reset-токены отзываются. Запросы ограничены по IP и аккаунту; токены не попадают в access-логи и Referer.

**AUTH-09. Транзакционные письма.** Используется отдельный почтовый адаптер с подтверждённым доменом отправителя. Отправка и её статус сохраняются в БД, временные отказы повторяются; недоставка видна пользователю и оператору. Конкретный поставщик SMTP/API выбирается до реализации этапа аккаунтов. Telegram не используется как единственный способ восстановления доступа.

## 6 Разрешённые адреса и мониторы

### 6.1 Заявка и одобрение адреса

**URL-01. Подача.** Подтверждённый пользователь отправляет точный URL и комментарий о принадлежности сайта. Приложение сохраняет pending-заявку; исходящий HTTP-запрос по ней не выполняется. Заявка сама по себе не создаёт работающий монитор и не занимает квоту активных проверок.

**URL-02. Формат.** Разрешены только http/https, DNS-имя публичного хоста и стандартные порты 80/443 для соответствующей схемы. Userinfo, fragment, IP-литералы, localhost и служебные имена запрещены. Нормализуются регистр схемы/hostname, IDNA, порт по умолчанию и пустой путь. Path/query не изменяются произвольно; адреса с секретными токенами не принимаются.

**URL-03. Решение.** Владелец рассматривает каждую заявку через защищённую CLI-команду: approved, rejected либо revoked. Фиксируются пользователь, нормализованный URL, время, оператор и причина. Перед одобрением проверяются публичность адреса, законная цель мониторинга и отсутствие служебных/внутренних ресурсов; при необходимости запрашивается доказательство контроля домена. Одобрение конкретного пользователя не переносится на другого.

**URL-04. Статусы.** Кабинет показывает решение и причину, дату подачи и рассмотрения. Ориентир работы поддержки — рассмотрение в течение двух рабочих дней; фактический график публикуется на сайте. Для rejected/revoked можно повторно подать тот же URL не чаще раза в сутки; переход обратно в pending сохраняет историю решений. Включённый монитор при этом остаётся приостановленным.

**URL-05. Проверка перед соединением.** Действующее approved-разрешение и безопасность конечного сетевого адреса проверяются перед каждым HTTP-запросом. Смена DNS не превращает ранее разрешённый URL во внутренний запрос. Небезопасный адрес получает blocked_by_safety, операторский сигнал и объяснение в кабинете; это не считается сбоем сайта.

**URL-06. Отзыв.** Отзыв разрешения запрещает новые проверки, сохраняет данные и даёт paused_by_moderation. Уже начатая проверка может завершиться. Возврат к approved также проверяет текущую безопасность адреса. Все решения и изменения причины доступны аудиту.

### 6.2 Управление мониторами

**MON-01. Создание.** name от 1 до 100 символов после strip, url до 2048 символов, is_enabled по умолчанию true. Создание возможно только по одобренному для этого пользователя URL; иначе 409 url_not_approved. URL и владелец после создания неизменяемы.

**MON-02. Уникальность.** Пара user_id + normalized_url уникальна. Дубликат, включая параллельное создание, даёт 409. Совпадение адресов у разных пользователей допустимо при отдельных одобрениях.

**MON-03. Изменение.** Можно менять name, is_enabled и telegram_notifications_enabled. Для другого URL подаются новая заявка и новый монитор. Физическое удаление монитора через API в версии 1.0 заменено выключением.

**MON-04. Отображение.** Кабинет показывает желаемую и эффективную активность, разрешение URL, причину паузы, последнее измерение, актуальность, состояние инцидента и доставки Telegram. До первых данных отображается unknown / «Нет данных».

**MON-05. Выключение.** Уже начатая проверка может сохраниться. С нового отбора монитор не проверяется. Выключение, тарифная пауза и отзыв разрешения не считаются восстановлением сайта; открытый инцидент завершается с отдельной причиной monitoring_paused.

**MON-06. Возобновление.** Каждый период наблюдения имеет observation_version. Пауза, отзыв разрешения, блокировка безопасности и возобновление меняют версию и сбрасывают счётчики под общей блокировкой состояния монитора. Старый инцидент не открывается повторно. История предыдущих периодов сохраняется до срока хранения.

## 7 Проверки и Telegram уведомления

### 7.1 Выполнение HTTP проверок

**CHK-01. Запрос.** GET, редиректы выключены, TLS-сертификат проверяется, тело ответа полностью не скачивается. Измеряется время до заголовков; соединение корректно освобождается. Проверка не выполняет JavaScript страницы.

**CHK-02. Исход.** 200–399 — успех; 400–599 — неуспешный HTTP-ответ. При 3xx оценивается исходный URL, адрес назначения не запрашивается. Промежуточные 1xx не сохраняются как финальный успешный результат; некорректный протокол классифицируется request_error.

**CHK-03. Сетевые ошибки.** timeout, connection_error, tls_error, request_error; при них http_status отсутствует. HTTP 500 не является connection_error. Защитный отказ URL, ошибка БД и отмена процесса записываются отдельно от исходов сайта.

**CHK-04. Время.** Общий бюджет получения соединения и заголовков — 5 секунд от начала самой проверки; ожидание слота семафора не входит. elapsed_ms измеряется монотонными часами; checked_at — начало проверки в UTC. Таймауты отдельных фаз HTTP-клиента не заменяют общий бюджет.

**CHK-05. Расписание.** Один worker начинает цикл при запуске. Следующий цикл начинается не раньше 60 секунд от начала предыдущего и после его завершения. Пропущенные циклы не догоняются; задержка расписания видна в метриках.

**CHK-06. Конкурентность.** Production-профиль — не более 10 HTTP-запросов одновременно на весь worker; значение конфигурируется и проверяется тестом. Один монитор имеет не более одной активной попытки. HTTP-клиент переиспользуется; конкурентные задачи не используют общую AsyncSession.

**CHK-07. Право.** После ожидания семафора и непосредственно перед запросом заново проверяются тариф, включение, одобрение URL и безопасность назначения. Окончание Pro не зависит от входа пользователя в кабинет.

**CHK-08. Сохранение.** Завершённая попытка имеет уникальный attempt_id и захваченную при запуске observation_version; повтор сохранения не меняет их. Транзакция не удерживается во время сетевого запроса. При сохранении под блокировкой состояния заново проверяются версия наблюдения и эффективная активность. Устаревшая/завершившаяся после паузы попытка сохраняется в истории, но не меняет текущие счётчики, инциденты и outbox. Для актуальной попытки сохранение, переход инцидента и запись outbox атомарны.

**CHK-09. Отказ БД.** Сохранение повторяется ограниченно с backoff; лимиты ожидания заданы конфигурацией. После исчерпания повторов потеря измерения отмечается метрикой/логом и операторским сигналом. Несохранённое измерение не влияет на статистику и инциденты. Непрерывность данных при отказе БД не обещается.

**CHK-10. Остановка.** SIGTERM прекращает выдачу новых задач; текущим операциям даётся до 15 секунд завершения, затем они отменяются с закрытием ресурсов. Отмена не записывается как падение сайта. Ограничение проверяется в Linux-контейнере.

**CHK-11. Актуальность.** Последняя запись старше 180 секунд означает «Данные устарели». Пропуск измерений не означает успешность или недоступность сайта. После длительного перерыва счётчики подтверждения сбрасываются.

### 7.2 Правила инцидентов

**INC-01. Открытие.** DOWN подтверждается двумя последовательными неуспешными сохранёнными попытками. Интервал между соседними попытками должен быть не более 180 секунд. Сохраняются first_failure_at и confirmed_down_at. До подтверждения одиночная ошибка видна в истории без Telegram-сообщения DOWN.

**INC-02. Восстановление.** Открытый инцидент закрывается после двух последовательных успешных попыток с тем же правилом интервала. Сохраняются first_success_at и confirmed_recovery_at. Новая ошибка до второго успеха сбрасывает счётчик восстановления.

**INC-03. Единственность.** У монитора не более одного открытого инцидента. Последующие ошибки внутри него обновляют данные, но не создают новые DOWN-сообщения. Повтор сохранения attempt_id не увеличивает счётчики.

**INC-04. Прерывание наблюдения.** Пауза завершает инцидент с monitoring_paused; длительный перерыв — с observation_lost, без RECOVERY. После возобновления статус unknown, затем новое подтверждение. Пользователю показывается, что восстановление сайта не установлено.

**INC-05. Интерпретация.** Длительность подтверждённого инцидента — оценка по наблюдениям, а не точное время простоя. Оба момента первой ошибки/успеха и подтверждения доступны в истории. Задержка обнаружения зависит от цикла и порогов; мгновенность не обещается.

### 7.3 Подключение Telegram

**TG-01. Канал.** Один личный чат Telegram на аккаунт. Подключение выполняется из кабинета с действующей сессией и CSRF. Пользователь сам открывает бота и запускает /start; произвольный chat_id от frontend не принимается.

**TG-02. Привязка.** Backend выдаёт deep link с одноразовым base64url-токеном из 32 случайных байт, в БД хранится хеш. Срок — 10 минут. /start резервирует токен за личным Telegram-пользователем; затем владелец подтверждает показанный аккаунт в кабинете до истечения срока. Повторный, чужой, просроченный токен и групповой чат отклоняются. До веб-подтверждения уведомления не отправляются.

**TG-03. Управление.** В кабинете доступны статус, отключение, повторная привязка и тестовое сообщение не чаще раза в минуту. Смена привязки меняет binding_version и отменяет неотправленные задания старой версии. Уже отправляемое сообщение может успеть дойти, что фиксируется в журнале. Перепривязка не пересылает старые инциденты автоматически.

**TG-04. Входящие обновления.** Production принимает webhook по HTTPS с отдельным secret_token и проверкой X-Telegram-Bot-Api-Secret-Token. update_id уникален; дубликат не повторяет действие. Успешный ответ возвращается после фиксации обновления/результата в БД; при недоступности БД — 5xx.

### 7.4 Доставка уведомлений

**NTF-01. События.** Обязательны DOWN и RECOVERY. Отключение уведомлений монитора атомарно отменяет его неотправленные задания; история и инциденты продолжаются. Повторное включение не восстанавливает отменённую очередь. Перед внешней отправкой dispatcher проверяет текущее предпочтение, привязку и её версию; уже начатая отправка может завершиться. Для непривязанного/отключённого Telegram фиксируется skipped, скрытого ожидания отправки нет.

**NTF-02. Содержание.** Сообщение содержит название монитора, безопасное имя хоста, тип события, время события UTC, краткую причину и ссылку на собственный кабинет. RECOVERY содержит сведения о соответствующем инциденте. Query-параметры, секреты, cookie и токены не передаются. Пользовательский текст экранируется, автоматические предпросмотры ссылок выключены.

**NTF-03. Outbox.** Намерение отправить сообщение создаётся атомарно с переходом инцидента в PostgreSQL. Уникальна комбинация incident_id + event_type + binding_version. Dispatcher выбирает задания с lease/статусом, отправляет вне транзакции и фиксирует результат. После перезапуска просроченный lease позволяет продолжить доставку.

**NTF-04. Порядок и повторы.** Для одного монитора события упорядочены по времени и ID; RECOVERY не обгоняет нетерминальный DOWN. Сетевые ошибки и 5xx повторяются с возрастающей задержкой от 5 секунд до 1 часа, не дольше 24 часов с момента события. 429 ждёт не меньше retry_after. Начальные ограничения — до 1 сообщения в секунду на чат и до 20 в секунду на бота.

**NTF-05. Терминальные ошибки.** Блокировка бота/недоступный чат прекращают автоматические повторы соответствующей привязки. Неверный bot token вызывает операторский сигнал. По исчерпании срока задание получает failed/expired, причина видна в кабинете; ручной повтор доступен оператору после устранения причины. Отправка устаревшего события обозначает исходное время и факт задержки.

**NTF-06. Гарантия.** Успешный ответ Telegram с message_id означает принятие сообщения API, а не чтение пользователем. После неоднозначного таймаута возможен повтор уже доставленного сообщения; exactly-once во внешнем чате не обещается. В БД событие создаётся один раз, а попытки доставки протоколируются.

**NTF-07. Измерение.** На управляемом стенде при исправных БД/Telegram и очереди до 20 сообщений каждая новая запись outbox должна начать отправку в течение 30 секунд. Для внешнего Telegram фиксируется фактическая задержка; гарантия доступности чужого API не заявляется.

Контракты интеграции сверяются с [Telegram Bot API](https://core.telegram.org/bots/api), [deep linking](https://core.telegram.org/bots/features#deep-linking) и [лимитами ботов](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this).

## 8 История и статистика

История сортируется по checked_at DESC, id DESC. Пагинация: limit по умолчанию 20, диапазон 1–100; offset >= 0.

Статистика принимает обязательные from и to с часовым поясом. Правила: from < to; период не более 31 дня; выборка from <= checked_at < to. API возвращает UTC.

**STAT-01. Поля.** total_checks, successful_checks, failed_checks, success_rate_percent, avg_response_ms, max_response_ms, daily, generated_at, history_available_from и truncated_by_retention. Если запрошенный период выходит за срок хранения, возвращается доступная часть с явным признаком усечения; отсутствующие измерения не считаются успехом.

**STAT-02. Формула.** success_rate_percent = successful_checks / total_checks × 100. Это доля успешных сохранённых попыток, а не точный процент времени доступности.

**STAT-03. Длительности.** Средняя и максимальная длительность рассчитываются только по успешным попыткам. Сетевые таймауты не смешиваются со временем успешного ответа.

**STAT-04. Пустая выборка.** Счётчики — 0, процент и длительности — null. Если попытки есть, но успехов нет, процент — 0, длительности — null.

**STAT-05. Дни.** Группировка по календарным дням UTC. В daily включаются только дни с попытками. Отсутствующий день не трактуется как 0% доступности.

**STAT-06. Точность.** Расчёты выполняются до округления. Процент и длительности округляются до двух знаков в ответе.

Контрольный пример: попытки 200/100 мс, 204/200 мс, 302/300 мс, 500/400 мс и timeout/5000 мс дают total=5, successful=3, failed=2, success_rate=60, avg_response_ms=200, max_response_ms=300.

## 9 Реальные платежи и возвраты

### 9.1 Создание покупки

**PAY-01. Заказ.** Подтверждённый пользователь выбирает Pro. Backend сохраняет purchase ID, тариф, снимок цены/валюты/30-суточного периода, пользователя и время до обращения к ЮKassa. Денежные значения точные; float для расчёта сумм не используется.

**PAY-02. Повтор запроса.** Пара user_id + Idempotency-Key уникальна. Повтор с теми же параметрами возвращает прежнюю покупку; с другими — 409. Стабильный Idempotence-Key для ЮKassa сохраняется заранее. Параллельные запросы не создают два списания.

**PAY-03. Адаптер.** Предоставляет создание платежа, получение подтверждённого платежа, получение/создание возврата и сверку. Создаётся платёж capture=true с metadata внутренней покупки и фиксированным return_url сервиса. Клиент перенаправляется на confirmation_url провайдера; банковские реквизиты сервис не собирает.

**PAY-04. Неизвестный исход.** Таймаут не означает ни успешную оплату, ни отмену. В течение гарантированного провайдером окна запрос можно повторить с прежним ключом и неизменными параметрами. Для ЮKassa окно идемпотентности — 24 часа; после него неизвестный create-payment запрещено повторять вслепую. Покупка переходит в reconciliation_required до безопасной сверки/операторского разбора.

### 9.2 Подтверждение и однократное применение

**PAY-05. Источник истины.** Return URL и данные браузера не активируют Pro. Backend запрашивает состояние платежа у ЮKassa собственными shop_id/secret_key и сверяет provider ID, recipient.account_id, сумму, RUB, metadata внутренней покупки, test=false и status=succeeded.

**PAY-06. Webhook.** Маршрут принимает type/event/object с ограниченным размером тела; перед изменением денег/доступа сведения проверяются через API. HMAC эмулятора не применяется к ЮKassa. Список IP провайдера может служить дополнительным ограничением, но не заменяет серверную сверку. Неизвестный provider ID не создаёт оплаченный заказ из полей webhook.

**PAY-07. Идемпотентное событие.** У ЮKassa не предполагается отдельный event ID: дедупликация по provider + object_id + event_type. Однократное начисление дополнительно защищено уникальным payment_id в журнале подписки и applied_at. Разные события одного платежа также не продлевают доступ повторно.

**PAY-08. Транзакция.** Фиксация подтверждённого успешного платежа, начисление периода, обновление paid_until и отметка обработки события выполняются атомарно. Две независимые покупки не теряют продления. Сетевой вызов ЮKassa выполняется вне длительной транзакции; порядок блокировок пользователя/платежа согласован с квотами мониторов.

**PAY-09. Ответ провайдеру.** HTTP 200 возвращается после надёжной записи задания на проверку в БД либо после завершённой обработки, включая дубликат. При недоступности БД — 5xx. ЮKassa повторяет доставку ограниченное время; корректность дополнительно обеспечивается сверкой.

**PAY-10. Состояния.** Хранятся отдельные local_status и provider_status. Статусы ЮKassa: pending, waiting_for_capture, succeeded, canceled. При выбранной одностадийной схеме неожиданный waiting_for_capture не выдаёт Pro и требует сверки. Локальная транспортная ошибка не выдаётся за статус провайдера failed. Подтверждённый succeeded не понижается старым событием.

### 9.3 Периодическая сверка и окружения

**PAY-11. Сверка.** Dispatcher не реже раза в 5 минут проверяет незавершённые покупки/возвраты и получает список возвратов магазина, включая операции уже успешных платежей. Используются пагинация, checkpoint и перекрывающиеся временные окна; найденные внешние возвраты проверяются API и импортируются идемпотентно. После простоя/восстановления БД проверяется весь пропущенный период. Сохраняются next_attempt_at, ошибка и результат. Неуспех сверки дольше 30 минут вызывает операторский сигнал; пользователь видит «Проверяем оплату», а не предложение немедленно заплатить повторно.

**PAY-12. Потерянный ответ.** При неизвестном provider ID выполняется согласованная процедура поиска операции по данным магазина/metadata и сверки с журналом. Нельзя создавать новую покупку для восстановления старой автоматически. Решение оператора, найденный ID и причина фиксируются в аудите.

**PAY-13. Разделение.** Разработка и CI используют заглушки и тестовый магазин ЮKassa. Production допускает только боевой магазин и реальные платежи; test=true отвергается для коммерческого начисления. Тестовые ключи, данные и маршруты эмулятора отсутствуют в production-конфигурации.

### 9.4 Возвраты и оплаченный доступ

**REF-01. Операция.** Запрос клиента поступает в поддержку. Оператор инициирует полный/частичный возврат через ЮKassa; сохраняются refund ID, payment ID, сумма, причина, инициатор и статус. Отображение «Возвращено» допускается только после подтверждённого succeeded-возврата. Платёж сохраняет исходную историю успешного списания.

**REF-02. Повторы.** Для создания возврата используется стабильный ключ; неизвестный исход обрабатывается как у платежей. Сумма подтверждённых возвратов не превышает сумму списания. Повтор webhook/сверки не применяет возврат второй раз.

**REF-03. Период доступа.** До отправки возврата оператор фиксирует согласованную корректировку конкретного начисления. Полный возврат снимает только неиспользованный остаток времени этой покупки; частичный — явно согласованное число оставшихся секунд, от нуля до остатка. Денежная пропорция не выводится из float автоматически. Уже использованный период не переносится в долг пользователю.

**REF-04. Другие покупки.** Корректировка применяется после подтверждения возврата под блокировкой пользователя и конкретного начисления с повторным расчётом его текущего неиспользованного остатка. При частичном возврате снимается минимум из согласованных секунд и текущего остатка; при полном — текущий остаток, включая ноль. Параллельные корректировки сериализуются. Начисления учитываются в очереди по времени применения; удаление будущего остатка сдвигает последующие периоды ближе, сохраняя их продолжительность и не создавая начало раньше now. При внешнем возврате без подготовленной корректировки доступ временно сохраняется, операция получает needs_access_review до решения оператора в течение рабочего дня.

**REF-05. Аудит.** Подтверждённые корректировки неизменяемы; исправление оформляется новой записью. Отменённый/неуспешный возврат не сокращает доступ. Для частичного возврата в приёмке проверяется сохранность времени другой покупки.

### 9.5 Условия настоящей оплаты

До включения продаж владелец определяет статус продавца, подключает и активирует магазин, согласует применимую схему чеков/фискализации и передаваемые сведения покупателя, публикует условия оплаты/возврата и контакты. Эти условия проверяются по актуальным требованиям провайдера и применимым правилам для выбранного статуса продавца. Коммерческий режим блокируется до подтверждения готовности.

При необходимости выдачи чека интеграция передаёт согласованные реквизиты и контролирует результат формирования; ошибка чека не скрывается оператором. ТЗ не подменяет выбор статуса продавца и юридическую проверку документов.

Основания интеграции: [процесс платежа ЮKassa](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process), [идемпотентность](https://yookassa.ru/developers/using-api/interaction-format), [уведомления](https://yookassa.ru/developers/using-api/webhooks), [возвраты](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds).

Таблица задаёт логические сущности; детализация физических полей и индексов фиксируется миграциями и архитектурным документом без ослабления ограничений.

- UNIQUE защищает email, URL пользователя, ключ создания покупки и provider IDs. Уникальность открытого инцидента обеспечивается БД.
- Все даты — с часовым поясом, расчёты в UTC. Суммы — целые копейки; длительности неотрицательны.
- checks содержит либо финальный HTTP-статус 200–599 без сетевой ошибки, либо сетевую ошибку без статуса; elapsed_ms >= 0.
- Каждое изменение схемы проходит Alembic. create_all не заменяет миграции. Начальные тарифы воспроизводимы.
- Подробные checks хранятся 31 сутки. Удаление выполняется ежедневно небольшими пакетами по checked_at без блокировки рабочего потока; граница хранения видна в API.
- Закрытые инциденты хранятся 90 суток от закрытия, доставки — 90 суток от терминального состояния. Открытые инциденты, текущие состояния мониторов и незавершённые задания не очищаются по возрасту; связанные записи удаляются в согласованном порядке. Одноразовые токены удаляются после срока и необходимого короткого аудита без исходного секрета.
- Финансовый журнал не удаляется очисткой checks. Конкретные сроки хранения финансовых/персональных данных определяются владельцем перед запуском с учётом его статуса и публикуются в правилах; техническая процедура удаления/обезличивания не нарушает обязательный учёт.
- Telegram chat_id и email не доступны другим пользователям и не используются для рекламы без отдельного основания. Резервные копии подчиняются описанному сроку хранения.

## 12 Redis и SQL

### 12.1 Кеш статистики

**CACHE-01.** Cache-aside: Redis → при промахе PostgreSQL → сохранение ответа с TTL 60 секунд.

**CACHE-02.** Ключ содержит версию формата, user_id, monitor_id и обе нормализованные UTC-границы периода. Эквивалентные временные границы должны давать одинаковый ключ.

**CACHE-03.** Авторизация и владение проверяются до выдачи результата из кеша. Кеш не содержит сессионных секретов.

**CACHE-04.** Новые проверки не требуют немедленной инвалидации. Ответ может быть устаревшим до TTL; generated_at показывает время расчёта.

**CACHE-05.** При ошибке чтения, записи, повреждённом значении или недоступности Redis запрос выполняется через PostgreSQL. Таймаут Redis ограничен, по умолчанию 200 мс.

### 12.2 Требования к SQL и измерениям

- Агрегаты выполняются в PostgreSQL; вся история не загружается в Python для расчёта API-статистики.
- Список мониторов не создаёт отдельный SQL-запрос на последний результат каждого монитора.
- В docs/sql.md приводятся параметризованные запросы с JOIN, GROUP BY, HAVING и оконной функцией получения последних трёх проверок каждого монитора.
- Для запросов конкретного пользователя ограничение владения обязательно.
- Генерируется набор минимум 100 000 checks для нескольких пользователей и мониторов.
- Для истории по monitor_id и checked_at сравниваются планы EXPLAIN (ANALYZE, BUFFERS) до/после подходящего индекса.
- В отчёте фиксируются запрос, объём данных, конфигурация окружения, планы и вывод. Наличие индекса само по себе не считается доказанным ускорением.
- Измеряется кеш-промах и попадание на одинаковом фиксированном периоде, включая число SQL-запросов.

**SEO-02. Структура.** Публичные страницы имеют осмысленные постоянные URL и обычные ссылки href. Для каждой индексируемой страницы — уникальный title, один основной H1, осмысленная description и canonical на её основной URL.

**SEO-07. Измерения.** Для главной и тарифов сохранить условия и результаты трёх мобильных запусков Lighthouse до/после, сравнить медианы. Рост позиций или посещаемости не является критерием приёмки.

## 14 Архитектура и безопасность

Стек: Python, FastAPI, Pydantic, HTTPX, asyncio, SQLAlchemy 2, asyncpg, Alembic, PostgreSQL, Redis, pytest, Ruff; React/Vite; Nginx, Docker Compose, GitHub Actions. Используются адаптеры ЮKassa, Telegram Bot API и транзакционной почты.

API, worker и dispatcher собираются из одного backend-образа и имеют разные команды. Общие правила тарифов, модерации и инцидентов не дублируются. API обрабатывает веб-запросы, worker выполняет проверки, dispatcher доставляет outbox и сверяет платежи. Очередь и финансовые данные переживают перезапуск Redis, так как хранятся в PostgreSQL.

**SEC-01. Защита исходящих запросов.** При создании заявки и перед проверкой валидируется URL; перед соединением проверяются все разрешённые DNS A/AAAA-адреса. Private, loopback, link-local, multicast, unspecified и служебные/metadata-адреса запрещены, включая IPv4-mapped IPv6. Соединение выполняется с проверенным адресом с сохранением правильных Host и TLS SNI; повторное неконтролируемое разрешение имени не должно обходить проверку.

**SEC-02. Egress.** Сетевые правила worker запрещают HTTP-доступ к внутренним/служебным сетям по IPv4 и IPv6, разрешая необходимые точные подключения к PostgreSQL и DNS. Редиректы выключены. Неявные proxy из окружения не обходят политику. Защита проверяется из контейнера; без её успешной проверки коммерческий запуск запрещён. Одобрение владельцем не заменяет сетевую защиту. Основа — [OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

**SEC-03. Секреты.** Пароли, session/reset/link-токены, bot token, Telegram webhook secret, SSH и ключи ЮKassa отсутствуют в Git, образах и frontend. Доступ ограничен процессами, которым они нужны; предусмотрены ротация и отзыв. URL Bot API с токеном редактируется при логировании.

**SEC-04. Публичная сеть.** PostgreSQL и Redis не публикуют порты в интернет. HTTPS обязателен; backend доверяет forwarded-заголовкам только Nginx. SSH ограничен оператором, сервисные контейнеры работают без root.

**SEC-05. Ввод и данные.** SQL параметризован, HTML и Telegram-текст экранируются. Логи не содержат Authorization, cookie, секретные query и платёжные реквизиты. Ошибки клиенту не раскрывают stack trace. Защищённые ответы не кешируются общим proxy.

**SEC-06. Среды.** Production, staging и CI имеют разные БД, ботов, домены и платёжные ключи. Тестовые события не выдают реальные права. Восстановленная копия production не отправляет Telegram/почту и не создаёт платежи до явной настройки изолированного режима.

**SEC-07. Аудит.** Модерация, изменение тарифов, возвраты, корректировки доступа и блокировки журналируются с инициатором и причиной. CLI требует доступ оператора и не превращается в открытый HTTP endpoint. Перед релизом проверяются зависимости и устраняются известные критичные уязвимости используемого пути выполнения.

## 15 Эксплуатация и условия запуска

### 15.1 Первый production профиль

Расчётная ёмкость первого запуска — до 20 зарегистрированных аккаунтов и до 100 одновременно проверяемых мониторов суммарно; каждый аккаунт может использовать полную квоту Pro. Профиль подлежит подтверждению нагрузочным тестом на выбранном VPS. Это ограничение ёмкости первой установки, а не тестовый режим оплаты или запрет коммерческого использования.

Лимит регистрации применяется атомарно, включая параллельные запросы; при заполнении регистрация закрывается до расширения мощности. Существующим аккаунтам зарезервирована возможность полной квоты Pro. Повышение ёмкости выполняется после повторного измерения worker, БД и очередей. В интерфейсе и документации указаны действующие лимиты.

На управляемом стенде при 100 адресах, concurrency=10, HTTP-бюджете 5 секунд и исправной БД цикл должен завершаться не более чем за 55 секунд. Для API истории/статистики выполняется 60-секундный тест с 10 клиентами на фиксированных данных: p95 не более 1 секунды, без неожиданных 5xx. Набор production-проверки содержит не менее 4,5 млн checks, что приближает 31 сутки максимального профиля; учебное сравнение индекса на 100 000 строк не заменяет этот тест. Фиксируются p50/p95, задержка очереди, CPU/RAM/диск и версия окружения. Чужие сайты не используются для нагрузки.

### 15.2 Контроль и отказы

**OPS-01. Наблюдаемость.** Логи содержат request_id/attempt_id/event ID, операцию, длительность и итог. Метрики различают ошибки сайта, своей БД, Redis, платежей и Telegram. Worker и dispatcher обновляют heartbeat не реже раза в 30 секунд независимо от наличия заданий.

**OPS-02. Внешний контроль.** Отдельная от основного VPS проверка контролирует HTTPS/readiness и возраст heartbeat; задержка более 180 секунд вызывает операторское уведомление. Отказ Telegram отслеживается также по независимому каналу, например email оператору. Контролируются заполнение диска, старейшее outbox-задание, незавершённые платежи и возраст backup.

**OPS-03. Деградация.** При отказе Redis статистика читается из PostgreSQL. При отказе PostgreSQL защищённые операции возвращают контролируемую 503; успешная оплата или доставка не выдумываются. Worker не интерпретирует собственные ошибки как падение сайтов. Недоступность ЮKassa временно запрещает новую оплату, сохраняя действующий доступ.

**OPS-04. Поддержка.** Есть рабочий контакт, процедуры обработки неопределённого платежа, восстановления аккаунта, возврата, отзыва URL и недоставленного сообщения. Инцидент сервиса и действия оператора фиксируются в журнале.

### 15.3 Резервные копии и восстановление

**OPS-05. Backup.** Автоматическая зашифрованная копия PostgreSQL минимум раз в сутки и перед миграциями; копия хранится вне основного VPS не менее 14 суток. Отдельно описано восстановление конфигурации и секретов из защищённого хранилища. Плановая цель RPO — до 24 часов, RTO — до 4 часов, подтверждённые учебным восстановлением; более строгие гарантии не заявляются.

**OPS-06. Restore.** Не реже раза в месяц и перед первым запуском копия восстанавливается в изолированное окружение. Проверяются схема, аккаунты, покупки, разрешения, история и очередь. До возобновления production выполняются сверка денег с провайдером и разбор возможных повторов уведомлений после потери недавнего состояния; восстановление старого outbox не должно автоматически отправлять всю старую очередь.

## 16 Docker и поставка

Compose запускает api, worker, dispatcher, postgres, redis и nginx. React-сборка раздаётся Nginx, публичный HTML приходит из FastAPI. Эмуляторы платежей/Telegram/почты доступны только в тестовом профиле.

- Закреплены зависимости и версия Python; frontend собирается воспроизводимо.
- Backend работает без root; .dockerignore исключает секреты и ненужные файлы.
- Слой зависимостей отделён от кода; сборка frontend использует отдельную стадию.
- PostgreSQL использует именованный volume; outbox и покупки не зависят от эфемерного диска контейнера.
- .env.example содержит описание настроек без рабочих значений секретов.
- Миграции выполняются одной задачей перед обновлёнными сервисами.
- Healthcheck БД проверяет готовность; исправный Redis не является условием запуска API.
- SIGTERM и restart проверены для API, worker и dispatcher.
- Egress/firewall-правила версионируются, применяются и проверяются на реальной сети контейнеров.
- README содержит проверенные команды конфигурации, сборки, миграций, тарифов, модерации URL, запуска, тестов, логов, остановки и восстановления.

## 17 GitHub Actions и CI CD

### 17.1 CI

На pull request и push:
1. Установка закреплённых зависимостей.
2. Ruff и проверка форматирования.
3. Подготовка тестовых PostgreSQL и Redis.
4. Миграции на пустой БД.
5. Unit- и интеграционные тесты.
6. Проверки и production-сборка frontend.
7. Сборка backend-образа.

Автоматические тесты не зависят от доступности сторонних сайтов, Telegram и настоящих списаний; внешние интеграции проверяются отдельным согласованным прогоном. Pull request не получает production-секреты. Падение проверки блокирует выпуск в release-workflow.

### 17.2 CD

После ручного успешного размещения автоматизировать выпуск из основной ветки:
1. Успешный CI.
2. Публикация образов с тегом commit SHA.
3. Резервная копия перед миграциями.
4. Остановка старых worker и dispatcher и короткое окно обслуживания записи. Webhook при недоступности фиксации получает 5xx; последующая сверка восстанавливает пропущенные платежные события.
5. Применение миграций одной задачей.
6. Запуск API, worker, dispatcher и frontend одной согласованной версии.
7. Проверка readiness и основного сценария чтения.
8. Проверка новой записи worker либо успешного пустого цикла, heartbeat dispatcher, обработки outbox и запуска сверки платежей без создания реального списания.

Два деплоя одновременно не выполняются. Старые и новые экземпляры worker/dispatcher не работают параллельно. Повторная отправка внешнего сообщения после неопределённого исхода учитывается по NTF-06. Volume не удаляется. При неуспехе workflow завершается ошибкой; результат не объявляется успешным.

Процедуры возврата образа и восстановления БД описаны отдельно. Возврат образа не откатывает схему автоматически. Бесшовное обновление не требуется. Обновление управляется через [механизмы deployment GitHub Actions](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments).

## Приложение А Учебные задачи вне обязательной приёмки

Эти упражнения не расширяют коммерческую функциональность релиза.

1. Рассчитать статистику по списку результатов за один проход через dict; сравнить с повторными проходами и результатом SQL.
2. Найти максимальную и текущую серию ошибок в упорядоченной истории за O(N) времени и O(1) дополнительной памяти.
3. После основной версии реализовать скользящее окно с deque и объяснить амортизированную сложность.
4. heapq для разных интервалов мониторинга рассматривается только при отдельном расширении расписания.

Решения сопровождаются граничными примерами и объяснением сложности. Для завершения основного релиза достаточно требований и критериев выше.
